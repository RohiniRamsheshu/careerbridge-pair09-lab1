audit did not assume that a prior run completed successfully because no original

## Root cause of the missing original experience

The active Batch 7 and Batch 3 environments were built with fresh, isolated
MySQL volumes and then populated with small synthetic records for Lab 2
verification. The Compose initialization mounts schema-only initialization;
the original bulk `seed_data.py` generator was not run against these volumes.
Consequently, the frontend can only display the small synthetic datasets that
exist in the active databases.

This conclusion is supported by:

1. The generator’s explicit 200/50/300/100/1,500 targets.
2. The active MySQL counts above.
3. The sanitized fixture names and their Lab 2 documentation/source locations.
4. Separate named volume and database identities for Batch 3 and Batch 7.

## Safest rollback approach

The verified dump contains the pre-restoration Batch 7 synthetic state and Lab 2
audit tables. If rollback is approved, first stop application writes, preserve
the dump and current post-restore backup, then restore the verified dump into a
separate disposable MySQL database or volume. Do not overwrite the active
database in place without a separately approved rollback window. Validate table
counts and health before pointing a frontend at the rollback environment.

The original Lab 1 generator can also be rerun safely only after reviewing the
current counts; it is additive and reaches targets but is not a substitute for
a point-in-time rollback backup.

Operational note: an early shell-quoting mistake during staging setup created an
empty disposable database named `$stagingDb` inside Batch 7’s MySQL container.
Read-only inspection found zero tables. It was not used by the application and
was intentionally not dropped because this batch prohibits destructive cleanup;
removing it requires explicit approval.

## Safest restoration approach (historical plan)

1. Preserve both existing Compose projects and all their volumes unchanged.
2. Create a third, uniquely named disposable Compose project with a fresh
   MySQL volume and a distinct host port.
3. Load the existing schema into that new volume only.
4. Use the original `seed_data.py` logic, after a separate review of its
   connection configuration, to populate the Lab 1 targets. Do not run it
   against either current project or the retained `handshake_lab1` database.
5. Validate the five target counts, sample only sanitized labels, and verify
   authentication with synthetic credentials before pointing any frontend at
   it.
6. If an older Pair 09 volume is later proven to contain the original data,
   prefer a read-only export into a new disposable volume over mounting it into
   Batch 7. Do not copy records directly into Batch 7 without a separate
   migration/compatibility review.
7. Keep Batch 7’s Kafka/Mongo/memory work on its existing volumes and use a
   separate Compose override or profile for the restored Lab 1 demonstration.

This approach restores the original application experience without replacing
or contaminating Lab 2 fixtures. Restoration, seed execution, volume mounting,
and any data copy require a separate explicit approval and were not performed
in this audit.
